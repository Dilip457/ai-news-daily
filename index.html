Concept of the Day

Mixture-of-Experts: why the biggest models got cheaper to run

How sparse activation lets an 816-billion-parameter model behave like a 42-billion-parameter one.

Meta's new Muse Spark Open carries 816 billion parameters, yet Meta says it runs at the speed of a 42-billion-parameter model. That gap is not marketing arithmetic; it is the whole point of a mixture-of-experts (MoE) architecture, and it is why open-weight models suddenly fit on a pair of desktop workstations.

In a standard dense transformer, every parameter is used for every token: feed in a word, and the whole network lights up. An MoE layer instead contains many separate experts — small feed-forward networks — plus a lightweight router. For each token the router selects only a few experts to run. Muse Spark Open has 256 experts and activates just 8 of them per token, so it computes with roughly 42 billion parameters even though all 816 billion must sit in memory.

That distinction matters for cost. Compute — the electricity and GPU time to process a token — scales with the active parameters, which is why MoE models can be far cheaper per token than a dense model of the same total size. Memory, however, scales with the total parameters, because every expert has to be resident and ready. This is why Muse Spark Open needs about a terabyte of unified memory to run locally, but then answers quickly.

The trade-off is why Apple's unified-memory Mac Studios became the launch vehicle. Apple's M5 Ultra can address up to 512GB per machine, so two paired Mac Studios hold the full model and the chip's high memory bandwidth feeds the small slice each token needs. Meta's framing — two Mac Studios behaving like one supercomputer — is a memory-bandwidth story as much as a model story.

MoE is not free of problems. Routing can be uneven, training is more complex, and quality depends on how well experts specialise. But the pattern is now standard across frontier releases, from Nvidia's Nemotron to Liquid AI's on-device models, because it is the most practical way to keep growing capability without growing per-token cost at the same rate.

The practical lesson for anyone evaluating models: stop reading parameter counts as a single number. Ask how many parameters are active per token, how much memory the full checkpoint needs, and what hardware it targets. Those three figures, not the headline size, decide whether a model is something you can actually run.
